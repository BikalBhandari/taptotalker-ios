# GitHub Triage

Triage issues on **this repo’s GitHub tracker** (`gh`) through a small state machine. Domain language lives in `CONTEXT.md`. Rejected enhancements are recorded under `.out-of-scope/`.

Every comment or issue body posted during triage **must** start with:

```
> *This was generated by AI during triage.*
```

## Reference

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — durable agent briefs for `ready-for-agent`
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` knowledge base
- [LABELS.md](LABELS.md) — GitHub label map + one-time setup

## Roles → GitHub labels

Exactly **one category** and **one state** label per triaged issue.

| Role | GitHub label |
|------|----------------|
| bug | `bug` |
| enhancement | `enhancement` |
| needs-triage | `needs-triage` |
| needs-info | `needs-info` |
| ready-for-agent | `ready-for-agent` |
| ready-for-human | `ready-for-human` |
| wontfix | `wontfix` |

State flow: unlabeled → `needs-triage` → `needs-info` | `ready-for-agent` | `ready-for-human` | `wontfix`. After reporter replies on `needs-info`, return to `needs-triage`. Maintainer overrides are allowed — flag odd jumps and ask first.

## Tooling

Use `gh` only (never invent issue state). Default repo is the current `origin`.

```bash
# Attention queues
gh issue list --state open --limit 50
gh issue list --state open --label needs-triage
gh issue list --state open --label needs-info

# Read / write
gh issue view <n> --comments
gh issue edit <n> --add-label "bug" --add-label "needs-triage"
gh issue edit <n> --remove-label "needs-triage"
gh issue comment <n> --body "$(cat <<'EOF'
> *This was generated by AI during triage.*

…
EOF
)"
gh issue close <n> --reason "not planned"   # wontfix
```

When replacing state labels, remove the previous state label in the same edit. Keep the category label.

If create/edit fails with 404 or permission errors, stop and tell the maintainer they need triage/write access (or a repo with push) — do not fake label changes.

## Invocation

Interpret natural language, e.g.:

- “Show me anything that needs my attention”
- “Let’s look at #42”
- “Move #42 to ready-for-agent”
- “What’s ready for agents?”

## Show what needs attention

Present three buckets, oldest first:

1. **Unlabeled** — open issues with neither category nor state triage labels
2. **`needs-triage`**
3. **`needs-info`** where the reporter commented after the last triage notes

Show counts + one-line summary each. Let the maintainer pick.

## Triage a specific issue

1. **Gather** — `gh issue view`, comments, labels; parse prior triage notes; explore code with `CONTEXT.md`; read `.out-of-scope/*.md` for similar rejections.
2. **Recommend** — category + state + short reasoning. Wait for direction.
3. **Reproduce (bugs)** — attempt before grilling; report repro / fail / needs-info.
4. **Grill** — if underspecified, clarify with the maintainer (and `CONTEXT.md` terms).
5. **Apply:**
   - `ready-for-agent` — comment with agent brief ([AGENT-BRIEF.md](AGENT-BRIEF.md)); set labels
   - `ready-for-human` — same brief shape; say why it can’t be delegated
   - `needs-info` — triage notes template below
   - `wontfix` + bug — explain, close
   - `wontfix` + enhancement — write `.out-of-scope/`, link in comment, close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md))
   - `needs-triage` — set label; optional progress comment

## Quick override

If the maintainer says “move #42 to ready-for-agent”, confirm labels/comment/close, then apply. Skip grilling. Ask whether they want an agent brief if none exists.

## Needs-info template

```markdown
> *This was generated by AI during triage.*

## Triage Notes

**What we've established so far:**

- point 1

**What we still need from you (@reporter):**

- question 1
```

## Creating issues

When asked to file an issue from chat/QA:

1. Draft title + body (disclaimer first).
2. Confirm with maintainer.
3. `gh issue create --title "…" --body "…" --label needs-triage` (add `bug` or `enhancement` if already clear).

## Branch workflow reminder

Implementation work for triaged issues follows the project rule: **feature branch → PR → approve → merge to `main`**. Never commit triage-driven code on `main`.
